# 模型选择问题排查与修复

用户报告新建助手无法切换模型，聊天模型更新显示固定的 legacy diagnostic conversation 错误。

## 当前真实证据

- 使用与本机 App 同一账号的 AK/SK，查询当前 Runtime 的 OpenAPI，确认 execution-config 支持 GET/PATCH。
- 创建临时普通助手，使用账号已开通且支持 Responses 的模型目录，PATCH 为 `kimi-k3-1-pro-261024`，GET 读回一致且执行配置版本从1升到2；临时助手删除成功。该检查重复通过。
- 当前 Runtime 有两个普通历史助手，均能读取模型配置；另一个诊断历史的 execution-config 返回404。诊断会话的上游运行入口只接受 Runtime 模型，未提供会话模型覆盖能力。
- 原前端对任何模型更新404都返回同一句“legacy diagnostic conversation”，会掩盖失败究竟来自诊断历史、普通配置还是不存在的资源。Chrome 的新建选择提交链路成功；用户描述的 macOS 点击问题未在该引擎复现，已改为防止焦点/滚动干扰并补真实按钮交互检查。

## 改动

- 模型选项鼠标按下时保留搜索框焦点，避免在 click 之前因 blur 卸载弹层；搜索框使用 `focus({preventScroll:true})`，避免自动聚焦带动表单滚动。
- 刷新执行配置时重置busy，避免旧请求被连接或配置版本变化取消后模型控件一直忙碌。
- Go 层遇到配置404后，只有诊断专属runs接口确认同一session时，才返回 `diagnosticModelUnsupported`；不因为启用trace就认定会话是诊断类型，也不会对诊断历史尝试重复创建修复。
- 前端提前标明已确认的诊断模型限制，并禁用该历史的模型选择，使用中英文说明；名称、指令与Skills编辑继续可用。普通助手的404保留原始错误，不再错误归类。

## 验证

- 临时普通助手真实模型PATCH/读回：通过，删除成功。
- 创建时选择模型、重试保留选择、保存后聊天同步：生产浏览器检查通过。
- 本机原生 WKWebView 加载生产构建和模拟服务，程序化操作选择并提交：通过，选中design-alternate，创建后聊天显示相同模型。复用脚本为 `scripts/verify-model-webkit.swift`。该检查覆盖WebKit引擎的前端事件和保存参数，不替代人工鼠标复测。
- 新增普通404误归类回归、诊断限制不阻塞指令保存回归：通过。
- 相关前端4文件29测试、TypeScript、设计检查通过。
- Go session/connection竞态检查通过。

## 限制

这次本机修复没有把已有诊断会话转换为普通助手；目前上游没有该会话的模型覆盖接口。普通助手的真实模型切换已验证成功。诊断历史的模型限制属于当前Runtime协议边界，不能通过仅改错误文案声称已支持。
